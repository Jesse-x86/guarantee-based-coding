# GBC 推荐围栏规则集（作者建议）

> 下面只是**作者个人开发哲学下的一种推荐调度方式**，不是 GBC 唯一或必然正确的用法，
> 更不是让 agent 替项目主人作治理决定。Agent 应优先契合主人已有的开发哲学与权限设计；
> 人类也完全可以自行规划、调整或探索其他 agent 分工与调度方式。
>
> GBC 本质上只是把行为依赖变成可重复自动测试的工具，不规定谁必须写代码、维护测试或调用工具。
> 欢迎把它当作基础能力，发展适合自己项目的工作流。以下规则是推荐默认，不是强制沙箱；真正的
> 强制边界仍要靠 agent 框架（例如 Claude Code 的 `pre-tool-use` hook）落地。
> **装了 GBC ≠ 自动安全，也 ≠ 接受了作者的工作方式。**

如果这套哲学适合你的项目，可以把下面的规则纳入 agent 指令（或用框架机制强制）：

1. **任何 agent 都不手编 GBC 管理的图与意图文件。** `gbc.md` 只经 GBC doc 工具修改；
   依赖与保证 JSON 只经 GBC 的 MCP / CLI 工具操作。父子投影、双向边与出生即绿都是
   确定性约束，绕过工具直接改文件会让它们漂移。实现对应的接口产物（若该语言/项目有）
   与保证测试则由实现者随代码一起维护。

2. **实现 subagent 对自己引入的局部契约负责。** 它不只写实现：还要查询现有保证、
   登记实际使用的依赖、优先复用已有保证；缺少所需行为保证时，自己写能真正变红的窄测试，
   再创建保证并用 `verify_*` 自证。未登记的行为依赖、未维护的保证测试都算任务未完成。

3. **意图与跨范围破坏仍由顶层 agent 把关。** subagent 只读 `gbc.md`，不得自行修改架构意图；
   退休/停用保证、跨文件重命名或重构等会影响其他任务的操作，除非 brief 明确授权，否则上报
   顶层 agent 协调。顶层 agent 负责对齐人类意图、限定任务范围、复核新增契约，并在 subagent
   交回后重新验证受影响保证和全局一致性。

4. **用框架机制落实“允许局部维护、禁止越界”。** hook 应拦截手编 `gbc.md` / 图元数据、
   subagent 修改意图以及未授权的跨范围破坏操作；不要一刀切屏蔽 subagent 的依赖登记、
   保证创建和验证，否则最了解实现依赖的人无法闭环维护契约。

5. **牢记边界的性质。** GBC 提供的是规则文本与引导，不是安全保证。
   真正阻止越权的是你的框架配置，请据此设置。
