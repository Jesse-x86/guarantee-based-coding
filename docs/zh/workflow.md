# 在 GBC 下工作

> 语言：**简体中文** | [English](../en/workflow.md)

本页讲**集成 GBC 后如何安全地改代码**：推荐工作流、意图文档怎么写、以及几个静默失效的陷阱。
概念见 [concepts.md](./concepts.md)，命令速查见 [reference.md](./reference.md)。

全文以面向 agent 的口吻写；人类也可读，或交给信任的 agent。内容基于「推荐 / 标准」场景，请按
实际权限划分灵活调整由 agent 处理还是留给人类决策。

---

## 角色默认：你是顶层 agent

本工作流默认**你是顶层 agent**。推荐流程：

**规划 → 对齐意图 → 派发任务 → 最终验收。**

- **规划**：弄清改动碰哪些文件夹，读**相关**的 `.gbc/<path>/gbc.md`（当前层，必要时祖先）。
  用 `gbc tree` 只在大任务开头做一次架构统揽，不是每次改文件的入门仪式。
- **派发**：优先派 subagent 做实现，按依赖拓扑（先 provider 后 dependent）。
- **最终验收**：subagent 交回后，**你**经 GBC 工具再跑受影响的保证。

小范围改动允许规划与实现一体；但日常编码不是顶层 agent 的默认职责。

---

## 两层契约

- **意图（gbc.md）** — 项目架构的唯一事实源，作为最高契约**由人类持有并审批**；agent 负责
  起草。改它经 `gbc doc`（MCP doc 工具 / CLI），绝不手编。
- **保证（Guarantee）** — 一个模块当前提供、且已被下游依赖的**具名行为承诺**。可以演进，但
  一旦要打破，必须先通知每一个 dependent，让它们同步修复。

---

## 两个相位，顺序至关重要

**在厘清架构前，切勿直接写代码。**

### 相位一：架构（草案先行，默认需人类显式批准后落库）

收到新需求时，把涉及的**所有** `gbc.md` 增量作为**草案**与人类核对；仅在获得**显式批准**后，
经 `gbc doc` 落库并跑 `gbc doc check` 确认一致。**已落库的 `gbc.md` 即为你实现的规范。**

> 默认安装会把「意图需确认」写进作业准则。如果人类主动要求从指令文件删掉这条确认规则，那么
> 这条规则就从你的上下文里消失，你可以更自动地行动——但随之而来的是更高的静默架构漂移风险。
> 只要规则还在，别私自搞一套「bypass」。

### 相位二：实现（机器门控）

推荐「一个子任务对应一个目标文件」（brief 里指明可写文件，其余**只读**）。按依赖拓扑（先被
依赖项）。任务执行方：

1. 读已批准的范围（brief / gbc.md）+ 接口 → 写实现。
2. 依赖的行为 / 新暴露的行为：签名级用 `add_dependency`；具体行为则**主动写窄测试并
   `create_guarantee` 登记**（优先复用已有保证）。**未登记的行为依赖 = 任务未完成。**
3. **局部自证**：只经 GBC 工具跑 `verify_provider` / `verify_guarantee`，**禁止**手跑
   `pytest`（手跑太容易「改测试装绿」，掏空门禁）。
4. 红了：恢复行为，或上报顶层让 dependents 适配。**禁止**为装绿而松测试 / 撤保证。
5. 中途发现意图有误 → 停，回相位一，禁止静默漂移。
6. 移动 / 改名走 `refactor_file` / `refactor_func` / `rename_guarantee`。

### 相位三：最终验收（顶层 agent）

任务执行方交回后，顶层再经 GBC 工具验证受影响的保证。**即使执行方自称全绿，也不跳过这步。**
绿了不必查图；红了再用 `who_depends_on` / `list_provides` / `list_depends_on` 看谁坏了、谁在乎。

## 意图文档怎么写

每个文件夹的意图存在 `.gbc/<path>/gbc.md`，分三段：

- **`# 意图`（Intent）** = 这个文件夹/文件**是什么、为什么存在**（角色 / 目的）。就地解释概念
  或留链接，别留未定义术语。
- **`# 内部约束`（Internal constraints）** = 它**需要什么、必须做 / 必须不做什么**（义务与
  规则：持有什么状态、消费什么、什么必须先于什么、什么绝不能碰）。只在本地存在、不向上冒泡。
- **`# 文件`（Files）** = 子文件夹（名字以 `/` 结尾）+ 本层代码文件，每个一行角色。

**三段其实是可见性作用域。** 分不清「意图 vs 约束」时，逐句问「谁需要知道这句话」：意图 =
外部要知道的（public 契约）；约束 = 所有内部文件要协调、外部不需要的（package-private）；
文件条目 = 只有该文件自己要知道的（private）。主要拿它当**「内部细节漏进意图」的嗅探器**——
实现底座（Pydantic vs dataclass）、磁盘布局、内部机制属约束 / 文件条目，不该住意图。

**写现状 + 禁令，不写与过去的 diff。** gbc.md 是**当前**契约。剔除这三类漂移诱饵：

- **阶段 / 版本词**（`MVP` / `v0` / `目前先`）：项目进度是全局事实，记在项目指令文件里，别在
  每个 gbc.md 重复。
- **路线图 / 愿望**（`日后演化为 X` / `为换后端预留接口`）：删掉，或移交路线图文档。
- **迁移叙事**（`不再用 X` / `改为 Y`）：要么是历史遗迹 → 删；要么是防回归禁令 → 改写成正向的
  `绝不 X` 约束。唯一合法的过去引用是**显式标注的历史注记**（`历史事实` / `兼容逻辑`）。

**spec-first**：派 subagent / 写代码前，先用 `gbc doc` 把意图写好、送审，再对着已写好的 gbc.md
实现。新建文件夹 / 文件时也**先登记它的意图 / `# 文件` 条目**，别等代码写完再补。

## 用 `[[项目相对路径]]` 引用代码

gbc.md 散文指向代码文件或符号时，写成 `[[app/core/models/game.py]]` 或
`[[app/core/models/game.py:GameSpec]]`——从仓库根出发、包在 `[[ ]]` 里的路径。**别用 `../`
相对路径**：相对引用在任一侧移动时失效，且从不同引用者看读起来不一样；而 `[[ ]]` 引用对每个
目标是一个规范字符串，目标移动时 `refactor_file` / `refactor_func` 会自动重写它。（数据目录、
HTTP 路由、ADR 链接不需要 `[[ ]]`。）

保证 id 遵循类似原则但**不含路径**：`<symbol>.<behavior>`（如 `make_game.returns_html`），
在提供方内部唯一即可。

## Agent 权力约束（安全建议）

为防架构漂移、防 subagent 为「装绿」私自删保证，建议通过框架配置（如 Claude Code 的
`pre-tool-use` hook）限制权限：

- **顶层 agent**：持全部权限。经 `gbc doc` 维护意图，经 GBC 工具管理保证图，做最终验收。
- **Subagent**：**禁用 GBC 修改类工具**（保证 / 依赖 CRUD、改意图）。配置成「只能读 gbc.md +
  用 `verify_*` 自证」。
- 强制力来自你的框架，跟走 MCP 还是 CLI 无关——同一个 hook 两边都拦得住。

## 窄测试准则

断言**行为承诺**，而非**内部实现**：`assert r is not None` 好于硬编码值；`with
pytest.raises(X)` 好于校验具体错误消息。**坚持「非窄不写」**——偶尔漏报可接受，但重构时因测试
写太死导致的误报会迅速侵蚀对验证系统的信任。

## 几个静默失效的陷阱

这几个最值得从第一天就记在脑子里，因为它们**静默**失效：

- **保证测试必须能变红。** 最致命的不是缺测试，而是 fixture 只走 happy path、行为坏了还一直
  绿。一条「非空」保证若 fixture 永远产不出空值，就什么都没守住。给 fixture 一条产出坏值
  （空 / None / 异常 / 重复）的路，确认承诺被违反时测试真的变红。**窄 ≠ 软。**
- **把你真正依赖的行为提升为具名保证。** 非空、非 None、抛异常、有序、幂等——这些是行为不是
  签名，免费符号依赖没有测试守护它们。经典的静默崩溃：上游把「非 None」弱化成「可能 None」，
  下游吃到 NoneType——因为「非 None」从没被命名。（仍默认免费符号依赖，只是别把**行为**依赖
  留成没命名的。）
- **保证变红时，恢复它或宣告它——绝不松测试。** 松 / 退保证来把红变绿，会静默把真保证降级成
  虚假安全。破坏是允许的，静默破坏不允许——红了要么把行为放回去，要么让每个 dependent 适配。

**每次登记依赖或保证时的嗅探测试**：「如果我在乎的那个行为现在就坏了，会有测试真的变红吗？」
若否，你手上就是一个装成保证的符号依赖，或一个装成测试的 happy-path fixture。先修那个。

## 常见坑速查

| 容易踩 | 改成 |
|---|---|
| 手编 `.gbc/**` 的 gbc.md 或 json | gbc.md 经 `gbc doc`；依赖 / 保证经 GBC 工具 |
| 想清架构就直接写代码 | 先起草 gbc.md → 人类批准（默认）→ 再拓扑实现 |
| subagent「顺手」改半棵树 | brief 写明可写目标文件，其余只读 |
| subagent 说全绿就跳过顶层 verify | subagent 自证；顶层仍做最终验收 |
| 测试断言具体返回值（`== "<html>..."`） | 断言承诺：非空 / 类型 / 抛异常 |
| 给每条依赖都命名保证 | 默认免费符号依赖，只懒升级行为依赖 |
| 退休仍有 dependents 的保证 | 先迁移 / 修 dependents（`retire` 会拒绝） |
| 用绝对路径调工具 | 永远用项目根相对的 posix 路径 |
| 一次改一大堆文件 | 拓扑序，每步一个文件，每步跑保证 |
| 移动 / 改名后手工修引用 | 用 `refactor_file` / `refactor_func`（幂等、连 `[[ ]]` 一起改） |

## 卡住了？`disable_guarantee` 是逃生口

重构中途 / 循环依赖卡住时，`disable_guarantee` 保留保证的 id 和边、暂缓它的出生即绿，让你不必
拆依赖就能做多步改动。`enable_guarantee` 会重跑出生即绿，仍失败则拒绝。被停用的保证始终**响亮**
——`gbc doctor check` 会一直报它，直到你 enable 回来，不会静默腐烂。
