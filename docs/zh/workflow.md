# 在 GBC 下工作

> 语言：**简体中文** | [English](../en/workflow.md)

本页讲**集成 GBC 后如何安全地改代码**：推荐工作流、意图文档怎么写、以及几个静默失效的陷阱。
概念见 [concepts.md](./concepts.md)，命令速查见 [reference.md](./reference.md)。

全文以面向 agent 的口吻写；人类也可读，或交给信任的 agent。内容基于「推荐 / 标准」场景，请按
实际权限划分灵活调整由 agent 处理还是留给人类决策。

随包的 **gbc-workflow** skill 可配合 MCP 或 CLI 使用；选择 CLI 时，用 **gbc-cli** 查询命令
语法。调用入口不改变权限与验收要求。`gbc setup` 会输出 skill 目录，可直接阅读；客户端需要
接入时沿用它的项目级约定，无需全局安装。

---

## 角色默认：你是顶层 agent

本工作流默认**你是顶层 agent**。推荐流程：

**规划 → 对齐意图 → 派发任务 → 最终验收。**

- **规划**：弄清改动碰哪些文件夹，读**相关**的 `.gbc/<path>/gbc.md`（当前层，必要时祖先）。
  用 `gbc tree show` 只在大任务开头做一次架构统揽，不是每次改文件的入门仪式。
- **派发**：优先派 subagent 做实现，按依赖拓扑（先 provider 后 dependent）。
- **最终验收**：subagent 交回后，**你**经 GBC 工具再跑受影响的保证。

小范围改动允许规划与实现一体；但日常编码不是顶层 agent 的默认职责。

---

## 两层契约

- **意图（gbc.md）** — 项目架构的唯一事实源，作为最高契约**由人类持有并审批**；agent 负责
  起草。改它经 `gbc intent`（MCP intent 工具 / CLI），绝不手编。
- **保证（Guarantee）** — 一个模块当前提供、且已被下游依赖的**具名行为承诺**。可以演进，但
  一旦要打破，必须先通知每一个 dependent，让它们同步修复。

## 两个相位，顺序至关重要

**在厘清架构前，切勿直接写代码。**

### 相位一：架构（草案先行，默认需人类显式批准后落库）

先收集证据：读相关意图、已有术语和决策，再检查受影响的接口、消费者、测试及实际故障。
区分已确认事实、推断与未决选择，说明目标和范围，给出推荐判断及依据。当前意图已覆盖的
缺陷修复可能不需要意图增量，不为走流程制造增量，也不重复请求批准同一个决定。

只有未决选择会实质改变行为、范围、兼容性、权限或难以逆转的决定，且现有证据无法解决时，
才向人类提问。可查的事实自己调查，范围内的普通实现选择自行处理。选择之间存在依赖时，
先解决影响后续方向的上游问题；给出建议和取舍，不逐项盘问实现细节。已有授权持续有效。

确需改变意图时，先起草**所有相关增量**，说明理由与仍未解决的选择，再写入。默认确认规则下，
新的增量仅在获得**人类显式批准**后经 `gbc intent` 落库，再运行 `gbc intent check`。
**已落库的 `gbc.md` 即为你实现的规范。** 工具一致性不等于设计获批；准备草案无需先写入受管意图文件。

> 默认安装会把「意图需确认」写进作业准则。如果人类主动要求从指令文件删掉这条确认规则，那么
> 这条规则就从你的上下文里消失，你可以更自动地行动——但随之而来的是更高的静默架构漂移风险。
> 只要规则还在，别私自搞一套「bypass」。

### 相位二：实现（机器门控）

推荐「一个子任务对应一个目标文件」（brief 里指明可写文件，其余**只读**）。按依赖拓扑（先被
依赖项）。任务执行方：

1. 读已批准的范围（brief / gbc.md）+ 接口 → 写实现。
2. 依赖的行为 / 新暴露的行为：签名级用 `add_dependency`；具体行为则**主动写窄测试并
   `create_guarantee` 登记**（优先复用已有保证）。**未登记的行为依赖 = 任务未完成。**
3. **局部自证**：只经 GBC 工具跑 `verify_provider` / `verify_guarantee`，**禁止**手跑
   `pytest`（手跑太容易「改测试装绿」，掏空门禁）。
4. 红了：恢复行为，或上报顶层让 dependents 适配。**禁止**为装绿而松测试 / 撤保证。
5. 中途发现意图有误 → 停，回相位一，禁止静默漂移。
6. 移动 / 改名走 `refactor_file` / `refactor_func` / `rename_guarantee`。

### 相位三：最终验收（顶层 agent）

任务执行方交回后，顶层再经 GBC 工具验证受影响的保证。**即使执行方自称全绿，也不跳过这步。**
绿了不必查图；红了再用 `who_depends_on` / `list_provides` / `list_depends_on` 看谁坏了、谁在乎。

## 意图文档怎么写

每个文件夹的意图存在 `.gbc/<path>/gbc.md`，分三段：

- **`# 意图`（Intent）** = 这个文件夹/文件**是什么、为什么存在**（角色 / 目的）。就地解释概念
  或留链接，别留未定义术语。
- **`# 内部约束`（Internal constraints）** = 它**需要什么、必须做 / 必须不做什么**（义务与
  规则：持有什么状态、消费什么、什么必须先于什么、什么绝不能碰）。只在本地存在、不向上冒泡。
- **`# 文件`（Files）** = 子文件夹（名字以 `/` 结尾）+ 本层代码文件，每个一行角色。

**三段其实是可见性作用域。** 分不清「意图 vs 约束」时，逐句问「谁需要知道这句话」：意图 =
外部要知道的（public 契约）；约束 = 所有内部文件要协调、外部不需要的（package-private）；
文件条目 = 只有该文件自己要知道的（private）。主要拿它当**「内部细节漏进意图」的嗅探器**——
实现底座（Pydantic vs dataclass）、磁盘布局、内部机制属约束 / 文件条目，不该住意图。

**写现状 + 禁令，不写与过去的 diff。** gbc.md 是**当前**契约。剔除这三类漂移诱饵：

- **阶段 / 版本词**（`MVP` / `v0` / `目前先`）：项目进度是全局事实，记在项目指令文件里，别在
  每个 gbc.md 重复。
- **路线图 / 愿望**（`日后演化为 X` / `为换后端预留接口`）：删掉，或移交路线图文档。
- **迁移叙事**（`不再用 X` / `改为 Y`）：要么是历史遗迹 → 删；要么是防回归禁令 → 改写成正向的
  `绝不 X` 约束。唯一合法的过去引用是**显式标注的历史注记**（`历史事实` / `兼容逻辑`）。

**spec-first**：派 subagent / 写代码前，先判断现有意图是否覆盖任务。确需修改时，先起草、取得
所需批准，再经 `gbc intent` 落库后实现。新建文件夹 / 文件时也**先登记它的意图 / `# 文件`
条目**，别等代码写完再补。

### 复用术语，保存决策理由

先查已有意图、概念文档、词汇表和决策记录。同一概念沿用同一名称；不同语境中的不同含义应
解释清楚，不强求全局统一。用具体例子和边界情况澄清歧义。例如 GBC 的免费符号依赖记录签名 /
存在性依赖，具名保证保护行为；只看到“依赖”一词或导入成功，无法判断消费者需要哪种承诺。

重要决定按项目已有文档约定保存所选边界及原因，区分已采用决定、被否决方案和待讨论提议。
已有词汇表或 ADR 就复用，不要求每个任务新建 CONTEXT、ADR 或术语文件。`gbc.md` 保留当前
职责与约束，需要时链接决策历史，不把讨论经过复制进去。例如 GBC 意图子系统把磁盘操作放在
`base`，CLI、MCP 和编辑器都是薄表面；新增编辑器功能应沿用此边界，除非变更已经获批。

## 用 `[[项目相对路径]]` 引用代码

gbc.md 散文指向代码文件或符号时，写成 `[[gbc/app/core/models/game.py]]` 或
`[[gbc/app/core/models/game.py:GameSpec]]`——从仓库根出发、包在 `[[ ]]` 里的路径。**别用 `../`
相对路径**：相对引用在任一侧移动时失效，且从不同引用者看读起来不一样；而 `[[ ]]` 引用对每个
目标是一个规范字符串，目标移动时 `refactor_file` / `refactor_func` 会自动重写它。（数据目录、
HTTP 路由、ADR 链接不需要 `[[ ]]`。）

保证 id 遵循类似原则但**不含路径**：`<symbol>.<behavior>`（如 `make_game.returns_html`），
在提供方内部唯一即可。

## Agent 权力约束（安全建议）

既要防架构漂移和「改测试装绿」，也要让最了解实现依赖的人闭环维护契约。建议通过框架配置
（如 Claude Code 的 `pre-tool-use` hook）按**操作性质**而非按「是否修改 GBC」一刀切：

- **所有 agent**：绝不手编 `gbc.md` 与图 JSON；统一经 GBC 工具维护。语言/项目特有的接口产物
  （Python 项目可能是 `.pyi`）与保证测试不属于机械图元数据，由实现者随代码维护。
- **顶层 agent**：经 GBC intent 工具维护人类持有的意图，限定任务范围，复核新增依赖/保证，
  协调跨范围破坏，并做最终验收。
- **Subagent**：只读意图，但随代码维护所需接口产物，并负责实现产生的局部契约：登记实际依赖、复用
  或创建所需保证、维护能真正变红的窄测试并 `verify_*`。默认不得退休/停用保证、修改意图或重构 brief 外文件；确需时
  上报顶层或取得明确授权。
- hook 拦的是手编元数据、意图修改和未授权越界操作；**不要屏蔽 subagent 的依赖登记、保证创建
  与验证**。强制力来自你的框架，跟走 MCP 还是 CLI 无关。

## 窄测试准则

先明确**消费者依赖的行为承诺**：谁通过哪个提供方接口，在什么输入或状态下，需要什么可观察
结果。创建新保证前先查询、复用已有合适保证；仅依赖签名 / 存在性时仍使用免费符号依赖。
选择能区分现实违约与正确行为的最小测试，经过真正承载承诺的边界。窄指范围聚焦，不是断言宽松。

消费者依赖精确值、顺序、错误或输出结构时，就应精确断言；只有非空 / 类型确实是全部承诺时，
才只检查它们，避免绑定偶然的实现细节。例如 GBC 编辑器 file-meta 契约区分非法路径
（**HTTP 400**）与缺少元数据（**HTTP 200 且 `meta: null`**）；只断言响应非空守不住前端需要的
区分。这些值来自现有契约，不代表本次重新执行了编辑器测试。

仓库中的真实例子是同一消费者的两个符号共享提供方的一条保证
（`tests/test_guarantee_deps.py`）：撤销第一个符号的依赖后，退休仍须被拒绝；撤销最后一个后，
才允许退休。这保护了消费者，而仅断言元数据对象存在会漏掉故障。其他消费者、其他提供方的
同名保证也应保持独立。

说明测试会捕获哪种合理的缺陷。在有帮助且已授权时，可以用受控回归或变异，经 GBC 验证其
辨识力，恢复代码后再验证；这不是所有任务强制先红的要求。导入失败、环境损坏，或 mock 直接
返回被断言的坏值，本身不能证明测试发现了目标缺陷。mock 可隔离外部边界，但不能替换保证
声称要保护的行为。实际执行结果、测试设计和未验证项分别说明。

**出生即绿保持不变**：创建保证和修改运行配置仍须通过现有门禁。它验证当前实现，不证明测试
能辨识未来缺陷；不要为登记失败测试而停用保证或削弱断言。

## 几个静默失效的陷阱

这几个最值得从第一天就记在脑子里，因为它们**静默**失效：

- **保证测试必须能发现目标缺陷。** 选有意义的输入 / 状态，观察真实承诺。happy-path 测试可能
  已足以保护该承诺；加入人为坏 fixture 不等于证明辨识力。按上面的窄测试准则解释它能捕获什么。
- **把你真正依赖的行为提升为具名保证。** 非空、非 None、抛异常、有序、幂等——这些是行为不是
  签名，免费符号依赖没有测试守护它们。经典的静默崩溃：上游把「非 None」弱化成「可能 None」，
  下游吃到 NoneType——因为「非 None」从没被命名。（仍默认免费符号依赖，只是别把**行为**依赖
  留成没命名的。）
- **保证变红时，恢复它或宣告它——绝不松测试。** 松 / 退保证来把红变绿，会静默把真保证降级成
  虚假安全。破坏是允许的，静默破坏不允许——红了要么把行为放回去，要么让每个 dependent 适配。

**每次登记依赖或保证时的嗅探测试**：「如果我在乎的那个行为现在就坏了，这个测试能发现该缺陷吗？」
若否，先改进测试，再把它当作保护。测试通过与边登记成功，本身不证明辨识力。

## 常见坑速查

| 容易踩 | 改成 |
|---|---|
| 手编 `.gbc/**` 的 gbc.md 或 json | gbc.md 经 `gbc intent`；依赖 / 保证经 GBC 工具 |
| 想清架构就直接写代码 | 先起草 gbc.md → 人类批准（默认）→ 再拓扑实现 |
| subagent「顺手」改半棵树 | brief 写明可写目标文件，其余只读 |
| subagent 说全绿就跳过顶层 verify | subagent 自证；顶层仍做最终验收 |
| 断言比消费者的承诺更弱或更严 | 断言所需行为；精确值属于契约时就精确检查 |
| 给每条依赖都命名保证 | 默认免费符号依赖，只懒升级行为依赖 |
| 退休仍有 dependents 的保证 | 先迁移 / 修 dependents（`retire` 会拒绝） |
| 用绝对路径调工具 | 永远用项目根相对的 posix 路径 |
| 一次改一大堆文件 | 拓扑序，每步一个文件，每步跑保证 |
| 移动 / 改名后手工修引用 | 用 `refactor_file` / `refactor_func`（幂等、连 `[[ ]]` 一起改） |

## 卡住了？`disable_guarantee` 是逃生口

重构中途 / 循环依赖卡住时，`disable_guarantee` 保留保证的 id 和边、暂缓它的出生即绿，让你不必
拆依赖就能做多步改动。`enable_guarantee` 会重跑出生即绿，仍失败则拒绝。被停用的保证始终**响亮**
——`gbc doctor check` 会一直报它，直到你 enable 回来，不会静默腐烂。
