# Guarantee-Based Coding (GBC)

**让 AI 修改代码时，不意外破坏其他功能。**

让 AI 改一个功能，往往很快。麻烦的是，它改完这里，另一个地方却坏了。

等测试或者 CI 报错，再让它回头修，当然也行。但有些弯路本来可以少走：
别的模块明明一直依赖这个行为，只是 agent 动手时不知道。

GBC 就是把这些约定记下来。这个模块负责什么，哪些地方依赖它，哪些行为不能随便改，
改完要跑什么测试——让 agent 动手前有东西可查，改完后有依据可验。

## 一行修改，为什么会弄坏没碰过的代码？

你让 agent 简化配置读取，它删掉了一个默认值：

```diff
- return config.get(key, "")
+ return config.get(key)
```

已有配置照常读取。但另一个模块依赖“缺失配置返回空字符串”，直接对结果调用 `.strip()`。
现在它拿到 `None`，就会报错——那个模块甚至没有出现在修改列表里。

在 GBC 中，这项行为是一条有名字、有测试的**保证**，使用它的模块被登记为消费者。
agent 可以在修改前查到这项依赖；修改后运行保证，覆盖缺失配置的检查就能发现破坏。

**谁提供什么行为 → 谁依赖它 → 用什么检查保护它。** GBC 持续维护这组关系，
让局部修改有明确的检查依据，也让失败能对应到被依赖的承诺。

架构也有类似的问题：功能跑通了，职责却悄悄放错了地方。GBC 的意图文档按目录记录当前职责、
内部约束和文件角色，帮助 agent 沿着已有设计修改；具体行为再由保证测试验证。

→ **[阅读完整案例：职责不漂移，行为不被意外破坏](docs/zh/walkthrough.md)**

## 怎么融入一次修改

1. **查相关上下文。** 围绕要改的文件查看架构意图、直接依赖和行为承诺，无需一次加载整棵项目文档。
2. **在边界内实现。** 沿用已有契约；需要改变职责或被依赖的行为时，先协调相应变更。
3. **验证并修正。** 在开发过程中运行相关保证，把检查失败反馈给 agent，修正后再验收。

GBC 通过 CLI 或 MCP 与你已有的 agent 配合，使用项目自己的测试。
它提供上下文和验证结果，agent 负责理解与修正；是否强制阻止提交或合并，由项目的接入和权限决定。

## 已经有 ADR、AGENTS.md 和 CI，还需要 GBC 吗？

它们可以一起使用。GBC 关注的是：**这次修改要遵守什么，哪些代码依赖它，怎样检查承诺还成立。**

| 已有工具或文档 | 主要回答 | GBC 补充什么 |
|---|---|---|
| ADR | 为什么做出这个架构决定？ | 按代码位置维护当前职责与约束，需要时引用决策历史 |
| AGENTS.md | agent 在项目里应该怎样工作？ | 可查询、由工具维护的意图结构和行为依赖关系；AGENTS.md 可以指导 agent 使用它 |
| 测试 | 这项检查现在是否通过？ | 具名行为承诺、提供方和消费者，以及对应的检查 |
| CI/CD | 何时、在哪里运行构建、检查和交付？ | 可在 agent 修改过程中或 CI 中调用的契约验证 |

ADR 和 AGENTS.md 都可以按模块拆分，CI 也可以快速反馈。GBC 的重点是将相关上下文、
行为依赖和可执行检查连接起来，而不只是拆分文档或提前运行测试。
更详细的区别见[核心概念](docs/zh/concepts.md#和已有概念的区别)。

## 快速开始

```bash
pipx install guarantee-based-coding
gbc setup
```

`gbc setup` 会打印接入 agent 的指南。按[快速开始](docs/zh/quick-start.md)完成安装、接入和冒烟验证。
也可以把 [Agent 上手指南](docs/zh/onboarding-agent.md)交给你的 agent，让它协助接入。

GBC 自身使用这套方法维护项目。支持 CLI / MCP，测试语言和框架通过执行器配置接入；
项目元数据放在 `.gbc/`，无需给业务代码添加专用注解。

**保护范围取决于已登记的契约和测试。** 依赖需要主动维护；未覆盖的行为不会自动得到保护。
架构意图指导修改，但自然语言约束不会自动变成可执行检查。测试及契约变更仍需审查。
GREEN 仅表示已执行项没有失败，验收还需确认所需检查实际执行。
